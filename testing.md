# @Generable Device Test — June 2026

**Date:** 2026-06-05
**Device:** iPhone (physical device)
**Architecture:** DataRetriever + @Generable structured output (no Tool protocol)

The Tool protocol approach was tested on 2026-05-09 and had fundamental reliability issues: the ~3B model repeatedly forgot it had tools, called the wrong tool, or hallucinated data. The @Generable approach eliminates the model's decision-making burden — it only extracts values from data already in the prompt.

---

## Key Differences vs Tool Protocol

| Aspect | Tool Protocol (old) | @Generable (current) |
|---|---|---|
| Data fetching | Model decides which tool to call | Swift DataRetriever.classify() |
| Output format | Free-text generated by model | Typed @Generable struct |
| Formatting | Model decides phrasing | Swift format functions |
| Reliability | ~40% of questions had issues | No crashes, no tool forgetfulness |
| Response speed | ~5-8s | ~3-5s (faster, less prompt overhead) |
| `unsupportedLanguageOrLocale` | Occasional | Eliminated |

## Remaining Issues

### 1. Classification mismatches
Some questions map to the wrong intent because `classify()` checks keywords sequentially:
- "top 5 longest" previously matched .longestRun before the top-N pattern could fire
- **Fixed:** `extractNumber(after: "top")` added before single-intent checks

### 2. "Always (Fastest)" label on RunListItem
The `@Guide` description "Optional label: Fastest, Longest, Steepest, Highest HR" reads as a picklist to the model, which always picks "Fastest".
- **Fixed:** Changed to "Optional descriptive label highlighting what makes this run notable compared to others"

### 3. GeneralResponse.answer too loose
For numeric questions (avg pace, total distance), the model sometimes outputs raw seconds `"345"` instead of formatted text.
- **Mitigation:** Precomputed stats include formatted values. `reasoning` field added so model thinks before answering.

### 4. Missing precomputed stats
`total_calories_kcal`, `total_elevation_metres`, `total_duration_seconds` were not in the precomputed data, so the model couldn't answer totals accurately.
- **Fixed:** All three now computed in Swift and injected as key-value pairs.

### 5. No split data
Q23 (km splits) has no HealthKit source for per-km split data. Mapped to `.general` which returns a non-split answer.
- **Not fixed:** Requires new HealthKit query based on distance milestones.

### 6. Recovery data limited
Q20 (HRV and sleep over last month) has only one data point. Recovery fetcher only queries around the last run date.
- **Not fixed:** Requires multi-date recovery fetch.

### 7. Bullet points in formatGeneral
`formatGeneral()` prepended `•` to each detail item.
- **Fixed:** Removed bullet characters. `details` array rendered as-is.

### 8. Pace comparison not caught
Q5 (faster than 4:30/km) is not classified as a pace-filter intent — just falls to `.general`. The model doesn't get a structured output field for filtering.
- **Not fixed:** Would need a new intent or a `mustBeFasterThan: Int?` field in SingleRunResponse.
